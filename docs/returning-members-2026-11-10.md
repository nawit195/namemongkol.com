# สมาชิกที่กลับมาใช้งาน

พัฒนาเมื่อ 10 พฤศจิกายน 2569 สำหรับ `/admin/returning-members` โดยยังไม่ติดตั้ง migration บน Supabase จริง ไม่ Commit/Push และไม่เผยแพร่ production

## นิยามและหน้ารายงาน

- สมาชิกที่ใช้งานอย่างน้อย 2 วันแยกกันภายในช่วงที่เลือก นับวัน `Asia/Bangkok` หลายกิจกรรมหรือหลายอุปกรณ์ในวันเดียวกันนับหนึ่งวัน
- เริ่มต้น 30 วัน เลือก 7/30/90 วัน หรือช่วงกำหนดเองรวมวันเริ่ม–สิ้นสุดไม่เกิน 365 วัน ไม่เกินวันนี้
- ค้นหาชื่อหรืออีเมล แสดงแพ็กเกจ จำนวนวัน วันแรก/ล่าสุด แหล่งข้อมูล และแบ่งหน้าละ 50 คน เรียงจำนวนวันมากที่สุดแล้วเวลาล่าสุด
- `บันทึกใหม่` หมายถึงทุกวันที่นับมีข้อมูล observed, `ย้อนหลัง` หมายถึงมีเฉพาะ legacy, `ใหม่และย้อนหลัง` หมายถึงมีทั้งวันที่พบข้อมูลใหม่และวันที่อาศัยข้อมูลย้อนหลังอย่างเดียว
- ตัวกรองข้อมูลใหม่เท่านั้นนับเฉพาะ observed; สรุปสมาชิกที่พบการใช้งานและสมาชิกที่กลับมาใช้ตัวกรองเดียวกับตาราง
- ตารางรองรับการเลื่อนแนวนอนบนมือถือ สถานะโหลด/ว่าง/ผิดพลาด/ไม่มีสิทธิ์ และยกเลิกคำขอเก่าเมื่อเปลี่ยนตัวกรอง

## การบันทึกและความปลอดภัย

`MemberActivityTracker` ทำงานเฉพาะหน้าสาธารณะและสมาชิกที่ไม่ใช่ anonymous เมื่อเปิดหน้า กลับมาแท็บ หรือเริ่มใช้งานวันใหม่ ไม่บันทึกแท็บที่ซ่อนอยู่ มีการยืนยันต่อบัญชีต่อวันในหน่วยความจำและ sessionStorage และรวมวันซ้ำในฐานข้อมูลอีกชั้นหนึ่ง ไม่สุ่มเก็บและไม่ขึ้นกับ sampled click analytics เดิม

POST `/api/member-activity` รับเฉพาะคำขอว่างหรือ `{}` ปฏิเสธ query parameters และข้อมูลที่ส่งมา เช่น user ID หรือวันที่ ใช้ผู้ใช้จาก `auth.getUser()` และวันที่จากเซิร์ฟเวอร์ ไม่มีชื่อที่วิเคราะห์ นามสกุล URL หรือเนื้อหาเครื่องมือในข้อมูลกิจกรรม

GET `/api/admin/returning-members` ตรวจ session และ `user_profiles.role = admin` ก่อนใช้ service role เรียก RPC ซึ่งรวมวัน ค้นหา นับ และแบ่งหน้าที่ PostgreSQL ทั้งสอง API ใช้ `Cache-Control: private, no-store` และไม่ส่ง service key ไปเบราว์เซอร์ บัญชีทั่วไปได้รับ 403 และผู้ไม่เข้าสู่ระบบได้รับ 401

ตารางใหม่เปิด RLS และไม่ให้ anon/authenticated อ่านหรือเขียนโดยตรง RPC เรียกได้เฉพาะ service_role ไม่เปลี่ยนสิทธิ์ตารางเดิม รายงานไม่รวมผู้ดูแลระบบ และไม่เชื่อมกิจกรรมก่อนล็อกอินเข้าบัญชี

## ติดตั้ง

ใช้กระบวนการ migration ของโครงการเพื่อติดตั้ง:

`supabase/migrations/20261110062709_member_activity_returning_members.sql`

Migration สร้างตารางรายวัน ตารางขอบเขตข้อมูล และ RPC พร้อมนำเข้าประวัติย้อนหลังสูงสุด 365 วันจากตารางที่มีอยู่ ได้แก่ `user_action_events`, `analysis_history` และ `credit_transactions` เฉพาะ `spend` โดยอ่านเฉพาะบัญชีและเวลา ไม่ใช้ `analysis_results` เพราะไม่มี user ID ตารางประวัติที่ไม่มีอยู่จะถูกข้ามและแสดงแหล่งที่นำเข้าจริงในขอบเขตข้อมูล

ข้อมูลย้อนหลังคัดเฉพาะบัญชีที่ไม่เป็น admin/anonymous และกิจกรรมตั้งแต่เวลายืนยันอีเมลหรือโทรศัพท์ เพื่อไม่ผูกกิจกรรมก่อนเปลี่ยนบัญชี anonymous เป็นสมาชิกย้อนหลัง หากไม่มีหลักฐานเวลายืนยันจะไม่นำเข้าประวัติของบัญชีนั้น ประวัติเดิมยังไม่ครบจากการสุ่มเก็บคลิก การล้างประวัติ และข้อมูลยืนยันบัญชี จึงมีข้อความกำกับชัดเจน ไม่ควรนำจำนวนนี้ไปตีความเป็นยอดผู้กลับมาทั้งหมดในอดีต

ต้องมี `SUPABASE_SERVICE_ROLE_KEY` ฝั่งเซิร์ฟเวอร์ หาก RPC/ตารางยังไม่ติดตั้ง API ตอบ 503 พร้อมรหัส `MIGRATION_REQUIRED` และหน้าแอดมินแสดงคำแนะนำติดตั้ง แทนรายชื่อว่าง

## ตรวจรับ

- `npm test -- --reporter=dot`: ผ่าน 63 files / 322 tests
- `npm run lint`: ไม่มี errors มี warnings เดิมของโครงการ 46 รายการ; ตรวจไฟล์ใหม่เฉพาะส่วนอีกครั้ง
- Production build ผ่าน รวม 220 static pages และ API ใหม่
- `scripts/test-returning-members.mjs` รัน migration จริงบน PGlite จำลอง: มากกว่า 1,500 events, สมาชิกเข้าเกณฑ์ 1,106 คน, แบ่งหน้า 50 คน, วันซ้ำ/ข้ามเที่ยงคืนไทย, ข้อมูลเก่า–ใหม่ทับวัน, คำค้นไทยและอักขระ %, admin/anonymous/กิจกรรมก่อนยืนยันบัญชี, RLS/สิทธิ์ service-only, ลบบัญชี และกรณีไม่มีตารางประวัติ ผ่านทั้งหมด
- เบราว์เซอร์ใช้ข้อมูลจำลองจาก `scripts/preview-returning-members.cjs` ตรวจค้นหา/ผลลัพธ์ว่าง/แบ่งหน้า/สลับ source/คำขอค้นหาช้าไม่ทับผลใหม่/ช่วงเกิน 365 วัน/503 และลองใหม่/401/403
- ตรวจ 320px, 390px และ 1280px ตารางเลื่อนในกรอบและปุ่มสัมผัสอย่างน้อย 44px
- Tracker ทดสอบเปลี่ยนหมวด รีเฟรช คลิกซ้ำ และสลับบัญชี สมาชิกแต่ละบัญชีส่งคำขอว่างหนึ่งครั้งในวันเดียวกัน
- Production build local: ทั้งสอง API ตอบ 401 และ private/no-store สำหรับผู้ไม่เข้าสู่ระบบ; เปิดหน้าแอดมินแล้วไปหน้าเข้าสู่ระบบตามระบบป้องกันเดิม

การทดสอบไม่อ่านรายชื่อสมาชิกจริงและไม่เขียนข้อมูลไปฐาน production หลังติดตั้ง migration จึงเริ่มสะสมข้อมูลใหม่จริงได้
