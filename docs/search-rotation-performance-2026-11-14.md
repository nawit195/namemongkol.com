# ลดเวลารอเปลี่ยนรายชื่อ /search

ปุ่มเดิมรอคำขอ seed ใหม่ทุกครั้ง แม้เพิ่งแสดง preview แล้ว และตัวอ่านข้อมูลเก็บเฉพาะแถวดิบในแคช ทำให้ทุกคำขอวนคำนวณคะแนน/เกรด/วันเกิดใหม่พร้อมอ่านหน้าข้อมูลต่อกัน

แก้ไข:

- เก็บผลคำนวณจากสูตรเดิมในแคชรายหน้า 1,000 แถว ใช้ tag public-names และ TTL 600 วินาทีเดิม เพื่อให้การ revalidate ยังครอบคลุมทั้งข้อมูลและค่าคำนวณ
- อ่านจำนวนแถวในหน้าต้น และดึงหน้าที่เหลือพร้อมกันครั้งละไม่เกิน 4 หน้า รองรับ schema เก่าและกรณีไม่มี count โดยยังอ่านตามลำดับเดิม
- เลือกหมวดแล้วใช้ preview ทันที เตรียม seed ของการหมุนชุดถัดไปในเบื้องหลังสำหรับตัวกรองปัจจุบัน
- ใช้คำขอที่กำลังทำงานร่วมกันระหว่าง prefetch กับการกดปุ่ม ไม่ส่งซ้ำ และไม่ใช้คำขอที่ตัวกรองเก่ายกเลิกแล้ว
- ผลเบื้องหลังไม่เปลี่ยนชุดที่แสดง ไม่เพิ่มจำนวนชื่อที่เปิดดู และไม่เรียกหักเครดิต

ผลตรวจ:

- ก่อนแก้ API บน production: ตัวอย่างคำขอใหม่ครั้งแรก 5,698ms, seed อื่นต่อเนื่อง 980/975ms (รวมเครือข่ายจากเครื่องทดสอบ)
- หลังแก้ API ในเครื่อง: คำขอแรก 4,827ms รวม compile/สร้างแคช, seed ต่อมา 173/149ms; ตัวเลขนี้ไม่ใช่การเปรียบเทียบเครื่องเดียวกันกับ production
- scripts/preview-search-rotation.cjs ใช้ ClientPage จริงกับ API จำลอง 1,800ms: เลือกหมวดแสดง preview โดยไม่ขึ้นสถานะรอ, กดชุดที่เตรียมไว้เปลี่ยนใน 73ms, แสดงเพียง 10 ชื่อ และแต่ละ rotation seed มีคำขอเดียว
- Unit tests ตรวจอ่านเกิน 1,000 แถวพร้อมกัน ค่าคำนวณไม่ทำใหม่เมื่อเปลี่ยน seed ผลรวม/เกรด/ตัวกรอง/การแบ่งหน้ายังตรงกัน และการ retry/ยกเลิกคำขอ
- Vitest 75 files / 403 tests ผ่านก่อนเพิ่มกรณียกเลิกคำขอหนึ่งกรณี; ชุดที่เพิ่มทดสอบแยกผ่าน และ production build ผ่าน

ไม่แก้ฐานข้อมูล สูตรวิเคราะห์ ราคา หรือเงื่อนไขโหลดเพิ่ม
